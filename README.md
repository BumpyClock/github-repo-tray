# GitHub Tray

A native C# / WinUI 3 notification-area app for your GitHub activity, inspired by
[RepoBar](https://github.com/steipete/RepoBar). It uses your GitHub CLI account and
supports GitHub.com only. It is not a full RepoBar feature-parity release.

## What it shows

- Activity generated by your account.
- Your recent authored pull requests, including open, closed, and merged PRs.
- Open pull requests awaiting your review.
- Recently pushed repositories, including private repositories your credentials
  can access.
- GitHub's last-year contribution calendar, with daily counts and a period total.
- Account-wide Copilot quota, when GitHub makes it available.

Activity reads the latest 30 events from GitHub's Events API, which can be delayed.
It is not a notifications inbox, followed-user feed, or contribution count.
Events for the same PR are grouped into one card, ordered by the latest event.
The event count covers only that fetched window, not the PR's entire timeline.
Pushes, issues, releases, and other non-PR events remain separate entries.
The other lists each contain at most 30 items.

PR cards show the author, branches, labels, review decision, and latest-commit CI.
Select the check summary to inspect checks or open the PR's checks page.
PR state, review decisions, and CI results are separate. Missing, pending,
unknown, cancelled, neutral, and skipped checks are not presented as passing.
Each PR includes up to 10 labels and 100 check contexts, including legacy commit
statuses. Truncated details disclose their total rather than claiming complete
progress. These are refresh snapshots, not streaming CI or standalone workflow
monitoring.

## Sign in

Install [GitHub CLI](https://cli.github.com/) and make `gh` available on your PATH.
Sign in from your own terminal:

```powershell
gh auth login --hostname github.com
gh auth status --hostname github.com
```

GitHub Tray reuses the account chosen by `gh`. It never starts sign-in
automatically or retrieves, displays, or stores tokens. `GH_TOKEN` and
`GITHUB_TOKEN` environment variables can take precedence over saved accounts.
To change a saved account, run `gh auth switch --hostname github.com` and refresh
the app. Repository permissions and organization SSO determine which private
data is available.

## Using the panel

The panel opens on launch. Closing it, pressing Escape, or moving focus away
hides it to the notification area. Reopen it from the tray icon. Use **Quit** to
exit; hiding the panel does not stop scheduled refreshes. If the tray icon is
unavailable, the panel stays open and offers **Retry tray**.

The footer contains Preferences, Refresh, and Quit. The tray menu provides Open,
Refresh, Settings, and Quit. **Refresh**, F5, and Ctrl+R request every dashboard
section regardless of its age.

### Contributions

The graph uses GitHub's GraphQL contribution calendar and reported intensity
levels, not estimates from events. Counts reflect what GitHub exposes to your
account. The header shows the total and a `12 months` label; the actual date range
is available to assistive technology.

Hover over a day for its date and count. The graph is one keyboard focus stop:
arrow keys inspect days, and Home/End select the first/latest day. Keyboard
selection shows a tooltip and is exposed through UI Automation. Refresh retains
the selected date when it is still available; otherwise it selects the latest
returned day.

**Preferences > Contribution cell size** offers Small, Medium, and Large.
Small fits the loaded year at the standard panel width. Medium and Large keep
larger square cells and scroll horizontally through older weeks. All seven
weekday rows remain visible. Reopening starts at the latest week on the right.
There is no zoom, legend, month/day axis text, or persistent day-detail strip.
The size saves automatically and survives restarts.

The panel follows Windows light, dark, and high-contrast themes. Loading cells
animate only while the graph is visible and system animations are enabled;
reduced motion and high contrast use static placeholders. A failed calendar
refresh shows an error without preventing other sections from loading.

### Copilot usage

The quota card shows the plan, percentage used, and reset countdown. Token-based
billing is labeled **AI credits**; legacy billing is **Premium requests**.
Unlimited chat/completion rows are omitted. Other unlimited quotas have no meter.
This is account-wide quota, not Copilot CLI session usage or an organization
billing report.

The app uses the same GitHub CLI sign-in:

```powershell
gh api --hostname github.com copilot_internal/user
```

No Copilot CLI installation or separate login is needed. Its account may differ
from the one selected in Copilot CLI. The read-only `copilot_internal/user`
endpoint is undocumented and may change or deny access for some accounts or
credentials. Failure affects only the usage section unless an account mismatch
is detected.

Percentage used comes from `100 - percent_remaining`; the app does not infer
request counts, currency, or credit units from other counters. The countdown
updates every minute while the panel is visible, without an API call. It shows
**Reset pending** after the reset time until fresh quota data arrives.

### Refresh and saved data

Refresh defaults to five minutes. Set an interval from one to sixty minutes in
Preferences, then choose **Save interval**.

| Section | Automatic reuse |
| --- | --- |
| Activity, My PRs, Reviews | At startup only, reuse a success younger than the configured interval. Periodic ticks fetch these sections. |
| Repositories, contributions | Reuse a success younger than 15 minutes. |
| Copilot usage | Reuse a success younger than five minutes. |

An age equal to the window requires a fetch. These windows do not add timer ticks
or immediate retry loops. Automatic reuse preserves the original success time
and any known section error. Manual Refresh bypasses all windows.

When a section fails, its eligible same-account last success remains visible and
is marked stale. On startup, saved data for the last-used account can appear
before account verification, labeled saved and unverified with its original
**Cached from** timestamps. A verification or network failure leaves it readable
with an error. A confirmed account change or mismatched API identity removes the
previous account's content; data from different accounts is never combined.

The cache is in the package's user-local data folder under `dashboard-cache`,
separate from `settings.json`. Records are partitioned by host and stable user ID.
Each section is reusable for less than seven days; reads and failed refreshes do
not renew that period. A successful empty response replaces older data.

**The cache can contain private repository metadata and Copilot quota details.**
It never stores credentials, authorization headers, or raw authentication errors.
Saved private data is deliberately readable before verification and after a
verification failure. It must not be mistaken for a verified live response.

**Preferences > Clear cached data** deletes the cache store's records for every
account and its last-used-account selector. It does not sign out of GitHub CLI,
delete credentials, reset preferences, or delete unrelated files. The currently
rendered dashboard may remain visible, but it is no longer reusable. The next
accepted refresh fetches every section. A manual refresh requested during
clearing waits for deletion, then runs one shared forced refresh.

Work started before clearing cannot recreate the deleted data. If some files
cannot be deleted, Preferences reports deleted and remaining counts; close
anything using those files and retry.

Hiding the panel releases its page and presentation rows, but keeps the native
window shell, settings, and refresh session. Reopening reconstructs the page from
current session state without waiting for another network refresh. The selected
section and preferences remain; popups close and list scroll positions reset.
This trades reopening work for less retained presentation state.

## Build and run

Development requires:

- Windows 10 version 1809 or later; Windows 11 is recommended.
- .NET 10 SDK and WinApp CLI 0.6.1 or later.
- Windows Developer Mode for development-package registration.
- Visual Studio 2022 or later, or Build Tools, with Desktop development with C++
  for NativeAOT publishing. ARM64 publishing also needs the ARM64 C++ tools.

From the repository root:

```powershell
dotnet build .\src\GitHubTray.App\GitHubTray.App.csproj -p:Platform=x64
winapp run .\src\GitHubTray.App\GitHubTray.App.csproj --arch x64 -p Platform=x64 --debug-output
```

Use project-mode `winapp run` to register and launch the development package,
not the packaged executable directly. Keep the architecture and `Platform`
consistent, including when adding `--no-build`. This is a full-trust WinUI 3
desktop app, not UWP; MSIX provides package identity and deployment.

Before redeploying, quit the app and let any previous `winapp run --debug-output`
session end. A debugger-attached instance can hold the package in servicing and
leave another launch waiting at **Checking for existing package**. Do not deploy
the package concurrently from multiple terminals or agent sessions.

### Native publishing and packaging

Release publishing uses NativeAOT. Debug builds retain the managed debugger
workflow. Use `publish`, not just `dotnet build -c Release`, to produce native code:

```powershell
dotnet publish .\src\GitHubTray.App\GitHubTray.App.csproj -c Release -p:PublishProfile=win-x64 -warnaserror
.\scripts\Test-NativeAot.ps1 -PublishDirectory .\artifacts\nativeaot\win-x64
```

Use `PublishProfile=win-x86` or `PublishProfile=win-arm64` for the other
architectures. Use a clean output directory when switching deployment modes.
Verification checks the NativeAOT runtime export and package resources and
rejects managed app/JIT payloads.

To build an unsigned bundle containing all three architectures:

```powershell
.\scripts\Build-MsixBundle.ps1
```

NativeAOT removes the installed .NET runtime requirement, not the Windows App
Runtime dependency or MSIX identity. Package the publish output and retain native
PDBs. The bundle must be signed before sideloading. See
[the release guide](docs/RELEASING.md) for output paths, signing requirements,
and runtime checks.

## Tests

```powershell
dotnet test .\tests\GitHubTray.Core.Tests\GitHubTray.Core.Tests.csproj
dotnet test .\tests\GitHubTray.AppState.Tests\GitHubTray.AppState.Tests.csproj
dotnet test .\tests\GitHubTray.App.Tests\GitHubTray.App.Tests.csproj
.\scripts\Test-RuntimeIdentifiers.ps1
```

Core tests cover API parsing, CLI failures, account identity, settings, and cache
persistence using fixtures and isolated files. AppState tests exercise the
production refresh session, including overlapping refreshes, cache clearing,
freshness, immutable publication, and shutdown. App tests source-link production
view models and presentation helpers to test selection, geometry, startup,
deferred check details, and hidden-panel behavior without WinUI. These tests need
neither live GitHub authentication nor network access.

CI builds the solution, runs these checks, and publishes/verifies x64 NativeAOT
with warnings treated as errors. It also tests both persistence stores with
reflection-based JSON disabled:

```powershell
dotnet test .\tests\GitHubTray.Core.Tests\GitHubTray.Core.Tests.csproj --filter "FullyQualifiedName~SettingsStoreTests|FullyQualifiedName~DashboardCacheStoreTests" -p:JsonSerializerIsReflectionEnabledByDefault=false
```

### Native contribution checks

With a loaded calendar in the running panel:

```powershell
powershell.exe -NoProfile -Mta -File .\scripts\Test-ContributionSelection.ps1 -AppPid <PID> -OutputDirectory .\artifacts\contribution-selection
powershell.exe -NoProfile -Mta -File .\scripts\Test-ContributionViewport.ps1 -AppPid <PID> -OutputDirectory .\artifacts\contribution-viewport
```

These require uninterrupted foreground access. The selection script checks
keyboard/pointer selection, focus, and UI Automation value/live-region events,
captures screenshots, and restores the original day. The viewport script checks
presets and horizontal history, restores the original size, and returns to the
dashboard. Pass `-SettingsPath <app-local-settings.json>` to also check persisted
cell size without changing the refresh interval.

Geometry checks exclude clipped edge cells and allow one device pixel of UI
Automation bounding-box rounding. Inspect the screenshots for exact square edges.

### Memory and reopen diagnostics

A hidden panel still retains WinUI, the native shell, and session data and still
refreshes on schedule. A nonzero footprint is not by itself evidence of a leak.
Releasing references does not guarantee an immediate resident-memory reduction;
garbage collection and native allocator reuse affect when pages return to Windows.

After the dashboard loads, hide it and sample its PID:

```powershell
New-Item -ItemType Directory -Force .\artifacts | Out-Null
.\scripts\Measure-IdleFootprint.ps1 -AppPid <PID> -OutputPath .\artifacts\idle-memory.json
```

The default is 15 samples two seconds apart. The report contains CPU time and
minimum/median/maximum private working set, total working set, and private
committed bytes. Private working set is process-unique resident memory; total
working set includes shared pages. Committed bytes need not be resident.
The script observes only; it does not hide the panel, force garbage collection,
trim memory, or change refresh settings.

Compare the same architecture, build configuration, account, tab, cache state,
warmup, and hide/show sequence. Debug includes a managed runtime and JIT;
NativeAOT publish does not. Include scheduled refresh cycles when investigating
background work, and measure reopening alongside hidden memory.

For opt-in reopen logging, run with `EnablePanelPerformanceDiagnostics=true` and
matching architecture settings. For example:

```powershell
winapp run .\src\GitHubTray.App\GitHubTray.App.csproj --arch arm64 -p Platform=ARM64 -p EnablePanelPerformanceDiagnostics=true
```

Do not attach a debugger for comparisons. Open and hide the loaded panel
repeatedly, then summarize its `LocalState` trace:

```powershell
.\scripts\Summarize-PanelPerformance.ps1 -TracePath '<LocalState>\GitHubTray-performance-<PID>.jsonl' -IdleFootprintPath .\artifacts\idle-memory.json
```

The idle-footprint input is optional and should come from the same process.
The summary excludes initial launch and reports sample counts, medians, and
ranges for preparation, the synchronous show call, and the first WinUI rendering
callback. That callback is a diagnostic proxy, not proof of compositor
presentation or input-to-display latency. Use equal workloads and sampling
cadence. Ordinary builds do not enable this logging.
